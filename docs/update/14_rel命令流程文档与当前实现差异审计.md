# `rel` 命令流程文档与当前实现差异审计

## 1. 文档目的

本文对照以下流程文档与当前源码，核实 `metaweave metadata --step rel` 的实际处理逻辑：

- `docs/6_rel命令执行流程详解.html`
- `metaweave/core/relationships/pipeline.py`
- `metaweave/core/relationships/repository.py`
- `metaweave/core/relationships/candidate_generator.py`
- `metaweave/core/relationships/scorer.py`
- `metaweave/core/relationships/decision_engine.py`
- `metaweave/core/relationships/writer.py`
- `configs/metadata_config.yaml`

本次审计只讨论 `rel` 的关系发现逻辑，包括外键直通、候选生成、语义过滤、评分、基数判断、决策抑制和结果输出。暂不讨论 JSON 新旧格式、字段路径及版本兼容问题，也不讨论 `rel_llm`。

## 2. 总体结论

HTML 文档与当前代码的总体结构基本一致：都采用五阶段流程，并使用相同的四维评分框架。但是，文档不能被视为当前实现的完全准确说明。

已确认的主要差异包括：

1. 物理外键候选去重实际没有生效。
2. 索引字段在语义过滤和名称阈值判断中的身份不一致。
3. 复合候选 Stage 1 对目标逻辑主键错误地应用了物理约束豁免。
4. 复合候选的同名兜底完全绕过目标字段语义过滤。
5. 单列候选存在文档未准确说明的同名字段语义豁免。
6. 低于接受阈值的候选被混入“抑制关系”，导致统计和原因失真。
7. 复合匹配实际支持目标组合的子集枚举，文档没有完整说明。
8. HTML 内部对名称相似度阈值的描述互相矛盾。

此外，文档和代码虽然在推断关系方向上保持一致，但该方向与物理外键方向及包含率公式不协调，属于需要在后续改造中单独解决的设计问题。

## 3. 已确认的逻辑差异

### 3.1 物理外键候选去重实际没有生效

#### 文档描述

阶段 1 收集物理外键签名，候选生成阶段检查候选签名；如果候选与已有物理外键重复，则跳过该候选。

#### 当前实现

`MetadataRepository.collect_foreign_keys()` 放入集合的是经过 MD5 计算的关系 ID：

```text
rel_a1b2c3d4e5f6
```

`CandidateGenerator._make_signature()` 返回的则是未哈希的文本签名：

```text
public.orders.[user_id]->public.users.[user_id]
```

候选生成阶段执行的是：

```python
if fk_sig in self.fk_signature_set:
    continue
```

由于集合元素和待比较值的格式不同，该判断无法命中。因此，文档所述的 FK 去重目前没有真正实现，已有物理外键仍可能再次形成推断候选。

#### 建议

Repository 与 CandidateGenerator 应共享同一个签名函数，并明确集合存储以下哪一种值：

- 统一存储原始规范化签名；或
- 统一存储计算后的 `relationship_id`。

同时必须明确关系方向，不能用“双方字段排序”代替关系方向归一化。

### 3.2 索引字段没有获得文档所述的“重要目标字段”阈值

#### 文档描述

单列目标字段只要属于 PK、UK、Index 或逻辑主键，就属于重要目标字段，使用较宽松的名称相似度阈值。

#### 当前实现

语义过滤阶段把以下索引标志作为强信号：

- `is_indexed`
- `is_composite_indexed_member`

这类字段可以绕过语义角色排除。

但是，选择名称相似度阈值的 `_is_qualified_target_column()` 只识别：

- 物理主键；
- 物理唯一约束；
- 单列逻辑主键。

该方法没有识别索引。因此，一个只有索引的字段虽然获得语义过滤豁免，却仍按普通字段使用严格阈值。

#### 实际影响

同一个索引信号在两个判断阶段具有不同含义：

| 判断阶段 | 索引是否属于强信号 |
|---|---:|
| 语义角色过滤 | 是 |
| 名称相似度阈值选择 | 否 |

#### 建议

先确定索引是否应当参与关系候选生成。如果保留索引信号，应使用一个共享谓词统一判断“重要目标字段”，避免两个阶段各自维护不同定义。

### 3.3 复合候选 Stage 1 没有过滤目标逻辑主键的语义角色

#### 文档描述

复合候选目标组合的语义规则是：

- 物理 PK、UK、Index：尊重数据库定义，不做语义过滤；
- 逻辑主键：应用 `composite.exclude_semantic_roles`。

#### 当前实现

Stage 1 的目标候选池同时包含：

- PK；
- UK；
- 逻辑主键；
- 多列索引。

但调用 `_match_columns_as_set()` 时，无论当前目标组合属于哪种类型，都固定传入：

```python
target_is_physical=True
```

因此，来自逻辑主键的目标组合也被当成物理约束，获得完全豁免，不会检查 `metric`、`description`、`attribute`、`complex` 等排除角色。

#### 建议

应根据 `target_combo_type` 决定是否应用语义过滤：

- `physical`：豁免；
- `index`：是否豁免由新的索引策略决定；
- `logical`：执行语义角色过滤。

### 3.4 复合候选 Stage 2 完全绕过目标字段语义过滤

#### 文档描述

Stage 2 使用大小写不敏感的同名匹配和类型兼容性检查，同时仍区分物理约束与逻辑约束的过滤规则。

#### 当前实现

Stage 2 对物理组合和逻辑组合统一调用：

```python
_find_dynamic_same_name(..., is_physical=True)
```

`_find_dynamic_same_name()` 在 `is_physical=True` 时会把目标表的全部字段放入同名匹配池，不检查语义角色。

因此，当前实际逻辑是：

> 只要复合字段名称完全相同且类型兼容，目标字段的语义角色就不会阻止它进入候选。

即使目标字段属于 `metric`、`description`、`attribute` 或 `complex`，也可能通过。

#### 建议

同名只能作为名称强信号，不能自动替代关联字段资格判断。Stage 2 应明确区分：

- 物理约束字段可直通语义检查；
- 逻辑主键和普通字段必须执行语义排除；
- 类型兼容性仍作为硬门槛。

### 3.5 单列候选存在未被文档准确说明的同名字段豁免

#### 文档描述

文档主流程表示：没有物理约束的目标字段需要应用 `single_column.exclude_semantic_roles`。

#### 当前实现

实际过滤优先级为：

1. 目标字段有物理约束或索引：不做语义过滤；
2. 源字段和目标字段大小写不敏感同名：不做语义过滤；
3. 其他目标字段：执行语义角色排除。

也就是说，普通同名字段本身也属于一种豁免条件。这个条件在文档主流程中没有准确体现。

#### 实际影响

两个表中完全同名的数值指标字段，即使都被识别为 `metric`，仍可能进入候选池。它们随后可能依靠数据交集、Jaccard 和名称得分获得较高综合分，形成误判。

#### 建议

删除“同名即跳过语义检查”的规则。同名应提高名称相似度，但目标字段仍需通过语义资格检查。物理 FK、PK、UK 是否豁免应由统一规则单独决定。

### 3.6 低分淘汰与复合关系抑制被混为同一类结果

#### 文档描述

文档将两个概念分开：

1. `composite_score < accept_threshold`：候选被直接丢弃；
2. 候选已经通过阈值，但同表对存在复合关系：按抑制规则决定是否保留单列关系。

#### 当前实现

`DecisionEngine.filter_and_suppress()` 最后执行：

```python
all_suppressed = below_threshold + suppressed
```

随后 Pipeline 将这个合并列表作为 `suppressed` 传给 Writer。Writer 对其中所有单列候选统一生成：

```json
{
  "suppression_reason": "在复合键中，无独立约束"
}
```

因此，单纯因为分数不足而失败的候选，也可能被记录为“因复合键而抑制”。

#### 实际影响

- `suppressed_count` 同时包含低分淘汰和真正的复合关系抑制；
- 输出的 `suppression_reason` 可能不符合事实；
- 低分单列候选可能被错误嵌入复合关系的 `suppressed_single_relations`；
- 审计时无法区分“评分不足”和“结构冗余”。

#### 建议

决策结果至少拆分为：

```text
accepted
rejected_below_threshold
suppressed_by_composite
```

只有 `suppressed_by_composite` 才能计入抑制统计并嵌入复合关系。低分淘汰如需审计，应使用独立的 rejected 结构和准确原因。

### 3.7 文档没有完整描述复合目标组合的子集枚举

#### 文档描述

文档重点描述对目标字段执行穷举排列，寻找与源复合键对应的最佳顺序。

#### 当前实现

当目标组合列数大于源组合列数时，代码会：

1. 从目标组合中枚举与源组合等长的所有子集；
2. 对每个子集继续枚举排列；
3. 从全部有效结果中选择最高分匹配。

因此，实际搜索范围不只是排列，还包含组合子集搜索。

#### 实际影响

源侧两列组合可以匹配目标侧三列索引或约束中的任意两列。这会扩大候选范围，也可能把一个更大复合约束的局部字段错误地视为独立关系。

#### 建议

后续设计需要明确是否允许复合约束的子集形成关系：

- 如果要求完整复合键匹配，应要求列数相等；
- 如果允许前缀索引匹配，应只允许符合数据库索引前缀语义的有序前缀；
- 不建议默认允许任意子集匹配。

### 3.8 文档中的名称相似度阈值不一致

HTML 不同位置出现了以下描述：

- 重要目标字段 `0.7`，普通字段 `0.85`；
- 重要目标字段 `0.6`，普通字段 `0.9`；
- embedding 模式的重要目标字段使用 `0.9`。

当前配置为：

```yaml
single_column:
  name_similarity_important_target: 0.6
  name_similarity_normal_target: 0.9

composite:
  name_similarity_important_target: 0.6
```

当前代码不会根据 `string` 或 `embedding` 方法自动切换阈值，而是直接读取上述配置。因此，当前 embedding 模式下的重要目标字段仍使用 `0.6`。

#### 建议

文档应只描述配置驱动行为，不应暗示代码会按照相似度算法自动切换阈值。若不同算法确实需要不同阈值，应在配置中显式分组，并分别通过样本评估确定。

## 4. 文档与代码一致，但设计需要重新评估的问题

### 4.1 推断关系方向与包含率方向不协调

当前推断候选从具有以下条件的字段出发：

- 物理主键；
- 物理唯一约束；
- 逻辑主键。

这些键字段所在的表被标记为 `source`，然后到其他表的 `target` 字段中寻找匹配。例如：

```text
users.id -> orders.user_id
```

物理外键直通采用的却是数据库外键方向：

```text
orders.user_id -> users.id
```

评分器的包含率定义是：

```text
|source 值集合 ∩ target 值集合| / |source 值集合|
```

对于 `users.id -> orders.user_id`，它判断的是“全部用户是否都下过订单”。这不能正确表达“订单中的 user_id 是否都能在 users.id 中找到”。

#### 风险

- 未被引用的主键值会降低包含率；
- 正确的隐式外键可能因为父表记录未被全部引用而得低分；
- 推断关系与物理外键在输出中的方向不一致；
- `N:1`、`1:N` 的含义需要结合不同方向解释。

#### 建议

后续统一使用数据库外键语义：

```text
引用字段（FK 侧） -> 被引用字段（PK/UK/逻辑主键侧）
```

包含率相应定义为：

```text
|引用侧非空值 ∩ 键侧值| / |引用侧非空值|
```

候选搜索可以仍然从键侧开始以缩小范围，但形成候选对象和执行评分之前，应转换为统一的 FK 方向。

### 4.2 复合源组合可能重复进入候选生成

`_collect_source_combinations()` 会分别收集物理 PK、物理 UK 和逻辑主键，但没有对相同字段集合去重。

如果一个复合物理主键同时出现在 `unique_column_sets` 中，同一字段组合可能以 `physical` 和 `logical` 两种来源重复生成候选。后续决策阶段也没有按完整关系签名统一去重，可能产生相同 `relationship_id` 的重复关系。

#### 建议

在源组合收集完成后，按规范化字段组合去重，并明确来源优先级：

```text
physical PK/UK > logical key
```

物理来源已覆盖的组合无需再次以逻辑来源加入。

## 5. 当前基本相符的流程

以下内容与当前代码基本一致：

1. 整体采用五阶段流程：加载及外键直通、候选生成、评分、决策、输出。
2. 物理外键直接进入结果，不参加四维评分。
3. 候选生成时先处理复合候选，再处理单列候选。
4. 复合源组合来自物理 PK、物理 UK 和达到置信度要求的逻辑主键，不包含源侧索引。
5. 单列源字段必须是物理 PK、物理 UK或达到置信度要求的单列逻辑主键。
6. 源候选字段不进行语义角色过滤。
7. 类型兼容性是候选生成阶段的硬门槛。
8. 四维评分及当前权重一致：

   | 评分维度 | 权重 |
   |---|---:|
   | inclusion_rate | 0.55 |
   | name_similarity | 0.20 |
   | type_compatibility | 0.15 |
   | jaccard_index | 0.10 |

9. 当前配置的接受阈值为 `0.65`。
10. 复合关系存在时，具有独立单列 PK/UK 的单列关系可以保留。
11. 普通索引不属于抑制阶段的独立约束。
12. 推断关系的基数判断使用采样唯一性和 JOIN 倍率。

## 6. 其他轻微差异

`RelationshipDiscoveryPipeline` 的类注释和阶段 3 日志仍然写着“6维度评分”，但评分器实际已经使用四维评分，HTML 文档在这一点上反而更接近真实算法。这属于旧文案，不影响实际结果，但应在修改 `rel` 时一并校正。

HTML 对单列目标字段的准入条件也存在内部矛盾：一处表示目标字段必须有约束或是逻辑主键，后续流程又明确允许普通字段以较高名称阈值参与。当前代码允许普通字段参与，因此应以详细流程为准，并修正文档概述。

## 7. 后续改造优先级建议

建议在适配下游数据读取之前，先确定 `rel` 的标准领域规则，再据此修改实现。处理顺序建议如下：

1. **确定统一关系方向和包含率方向。** 这是后续所有评分、基数、去重和输出语义的基础。
2. **修复物理外键去重。** 避免同一关系同时以物理外键和推断关系出现。
3. **统一候选字段资格判断。** 明确 PK、UK、逻辑主键、索引及普通字段各自的准入与豁免规则。
4. **删除同名字段的语义豁免。** 同名只影响名称得分，不替代语义资格检查。
5. **修正复合目标逻辑主键过滤。** 逻辑发现结果不应冒充物理约束直通。
6. **确定复合约束是否允许任意子集匹配。** 默认建议只接受完整组合，索引场景最多接受合法前缀。
7. **拆分低分淘汰和结构抑制。** 保证审计统计及原因准确。
8. **去重候选与最终关系。** 同一完整关系只保留一个候选，并记录最可信来源。
9. **统一配置和文档阈值。** 阈值完全由配置决定，并通过测试数据校准。

在这些规则确定后，`rel` 可以形成一条清晰的标准流程；未来 `rel_llm` 只需在标准候选池之外增加 LLM 候选来源，再复用相同的资格检查、评分、决策、去重和输出流程。
