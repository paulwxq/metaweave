# 3. REST API 与 Docker Compose 改造顺序建议

日期：2026-09-10  
状态：架构讨论与实施顺序建议，尚未实现 REST API 或容器部署。

## 1. 结论

用户已同意使用 Docker Compose 统一启动系统，并明确后续需要 REST API 提交作业和查询状态。

结合这一目标，建议顺序为：**先设计统一作业架构，提取业务服务并实现 REST API 与后台执行闭环，再完成 Dockerfile 和 Compose 部署。**

数据库可以在开发阶段提前通过 Compose 启动，Python 镜像也可以提前验证依赖安装。推荐顺序强调的是：最终容器结构应由作业执行架构决定，无需等全部 API 完成后才开始 Docker 相关工作。

CLI 应长期保留，容器化和 REST API 不会取代手工执行能力。

## 2. 改造量判断

单独把现有 CLI 和依赖服务容器化，改造量相对有限，主要涉及部署配置、路径、权限与连接配置，核心元数据处理逻辑基本可以复用。

| 工作 | 内容 | 主要影响 |
|---|---|---|
| Python 镜像 | Dockerfile、锁定依赖安装、工作目录和 CLI 路径 | 新增部署文件 |
| Compose 编排 | Python、PostgreSQL、Milvus、Neo4j 及所选 Milvus 部署所需组件 | 服务配置 |
| 网络与连接 | 容器间通过服务名访问，支持外部源数据库 | 连接配置 |
| 持久化 | 数据库持久卷，输出、日志和配置挂载 | 路径及权限 |
| 初始化与健康检查 | 服务就绪检查、目标数据库和集合初始化 | 启动流程 |
| 集成验证 | 生成、加载、重启和数据持久化验证 | 测试与运行检查 |

REST API 作业管理的改造量更大：它需要解决后台执行、状态持久化、并发、输出隔离和异常恢复，不能简单理解为给 CLI 增加几个 HTTP 路由。

以上是基于当前结构的定性评估，尚未形成详细任务拆分或工期估算。

## 3. 为什么最终建议先做作业服务与 API

### 3.1 作业执行方式决定容器结构

需要先明确以下问题：

- API 收到请求后如何提交后台作业。
- 作业由 API 进程执行，还是交给独立 worker。
- 作业状态如何持久化。
- 进程重启后，运行中的作业如何标记、重试或恢复。
- 多个作业如何隔离文件输出与数据库写入。
- CLI 作业是否进入统一的作业列表。

这些决定会影响 Compose 中的服务数量、启动命令、挂载、健康检查，以及是否需要额外队列组件。目前尚未确定具体队列、API 框架或 worker 实现。

### 3.2 两种实施顺序都可行，但适用目标不同

| 顺序 | 适合情况 | 主要代价 |
|---|---|---|
| 先 Compose，再 API | 急需交付现有 CLI 容器版本，API 需求尚未确定 | API 实现后可能重新调整容器结构 |
| 先作业服务与 API，再完成 Compose | 已明确异步作业接口，计划整体发布 | 完整容器交付稍晚，但部署与执行架构更一致 |

前期讨论曾建议先容器化再增加 API，其出发点是尽快获得可运行的 CLI 容器。重新审视整体目标后，推荐采用第二种顺序。

为方便进入容器而让 CLI 进程空闲常驻，可作为临时运维方案，但没有必要作为最终服务架构。

## 4. 推荐实施步骤

### 第一步：设计统一作业模型与执行边界

明确作业标识、输入参数、状态转换、进度、结果位置与错误信息，并确定并发限制、超时、输出隔离和重复提交处理方式。

同时区分三种不同能力：

- 查询作业当前状态。
- 失败后重新执行作业。
- 从已完成阶段继续执行。

第三种能力需要更细的检查点和幂等设计，不能因为已有状态表就认为具备断点恢复能力。

### 第二步：提取可复用业务服务

从 CLI 编排代码中提取可供程序直接调用的服务入口，让 CLI 和 REST API 共用业务实现：

```text
CLI 命令 ─────┐
             ├─ 业务服务 → 元数据生成、关系发现、数据加载
REST API ────┘
```

API 不应依靠拼接 shell 命令执行 CLI 来复用功能。CLI 参数解析和 HTTP 请求解析各自保留，核心业务与作业执行逻辑共享。

### 第三步：实现 REST API 与后台作业闭环

先完成以下最小闭环：

```text
提交作业 → 返回作业 ID → 后台执行 → 查询状态 → 获取结果
```

验证状态持久化、失败报告和并发隔离后，再扩展取消、细粒度恢复等能力。具体 URI、状态枚举及 API 框架将在接口设计中确定。

### 第四步：完成 Dockerfile 与 Compose

根据前面确定的执行模型配置最终部署：

- Python 应用镜像按锁文件安装依赖，配置工作目录及 CLI 命令路径。
- API 与 worker 如需分开运行，可使用同一个镜像、不同启动命令。
- PostgreSQL 保存业务与作业状态，Milvus 保存向量，Neo4j 保存图关系。
- 暂不启用 pgvector，与第 2 份选型建议保持一致。
- 为数据库配置持久卷，为作业产物配置持久化存储。
- 明确环境变量注入、健康检查和初始化顺序。

不要将宿主机的 `.venv-wsl` 或 `.venv-win` 复制进镜像，容器内应构建独立的 Linux 运行环境。

### 第五步：验证 CLI 与 API 共存

检查 API 提交和 CLI 手工作业能否按设计共享业务能力，并验证：

- 输出和日志可在容器重建后保留。
- 多个作业不会互相覆盖文件。
- 清空、重建和增量写入不会互相干扰。
- 服务重启后状态可解释，不会永久显示失真的“运行中”。
- 失败作业能够按既定策略重试或恢复。

## 5. 容器内手工执行 CLI

以下命令为规划示例，假设 Compose 服务名为 `metaweave`，镜像已配置工作目录并将 CLI 加入 PATH。当前尚未创建对应 Compose 文件，不能视为已可运行的部署命令。

### 5.1 进入正在运行的容器

```bash
docker compose exec metaweave sh

# 在容器内执行
metaweave --help
metaweave metadata --config configs/metadata_config.yaml --step ddl
```

也可从宿主机直接执行：

```bash
docker compose exec metaweave \
  metaweave metadata --config configs/metadata_config.yaml --step ddl
```

`exec` 要求目标容器正在运行，它在容器内启动一个新进程，无需安装 SSH 服务。后续 API 常驻运行时，仍可通过这种方式执行 CLI。参见 [Docker Compose exec 文档](https://docs.docker.com/reference/cli/docker/compose/exec/)。

### 5.2 使用临时任务容器

在只有 CLI、没有常驻应用进程时，可以使用：

```bash
# 交互式 shell
docker compose run --rm metaweave sh

# 执行一次作业
docker compose run --rm metaweave \
  metaweave metadata --config configs/metadata_config.yaml --step ddl
```

临时容器复用服务定义中的环境和挂载，退出后删除容器。写入持久卷或宿主机挂载目录的产物会保留；只写入临时容器可写层的文件不会保留。`run` 默认不发布服务端口，因此 API 服务应通过正常的服务启动方式运行。参见 [Docker Compose run 文档](https://docs.docker.com/reference/cli/docker/compose/run/)。

### 5.3 CLI 与作业列表的关系

直接执行 CLI 不会天然出现在 REST API 的作业列表中。如果需要统一查看，CLI 也应接入同一套作业登记与状态更新机制。

即使使用临时容器，挂载目录和目标数据库也可能与 API 作业共享，不能把容器分开理解为作业数据已经隔离。

## 6. 部署边界与注意事项

### 6.1 被分析数据库可以位于 Docker 外部

Compose 中的 PostgreSQL 可以专门承担系统状态存储。现有业务库或客户数据库仍可作为外部数据源连接，不需要为容器化迁移业务数据库。

容器连接其他服务时使用相应服务名或外部地址；容器内的 `localhost` 指向当前容器自身。

### 6.2 启动顺序不等于服务就绪

仅声明依赖启动顺序不能保证数据库已可处理请求。应为适用依赖配置健康检查及 `service_healthy` 条件，并保留应用层连接错误处理。健康检查也不能代替应用所需数据库、表或集合的初始化。

参见 [Compose 启动顺序官方文档](https://docs.docker.com/compose/how-tos/startup-order/)。

### 6.3 开发阶段可以提前使用 Compose

优先设计作业架构不妨碍提前启动容器化数据库、验证网络、路径挂载和 Python 镜像依赖。暂时不需要为这些开发配置确定最终 API/worker 划分。

## 7. 待确定事项

- API 与 worker 是否拆为独立进程及容器。
- 作业提交与领取机制，是否需要额外队列服务。
- CLI 作业是否统一登记到 API 可查询的作业列表。
- 首期是否要求取消和断点恢复，或仅提供状态查询与失败重跑。
- 作业输出路径、数据集更新范围与多作业并发规则。
