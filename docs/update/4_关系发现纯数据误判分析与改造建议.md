# 4. 关系发现纯数据误判分析与改造建议

日期：2026-09-10  
状态：代码分析与改造建议，尚未修改关系发现逻辑或配置。

## 1. 问题与结论

用户在实际使用中发现：两个字段名称和业务含义不同，但均为整数编号，样例值的包含率、交集和并集相关指标较高，可能被误判为关联字段。

例如：

```text
customers.customer_id：1、2、3、4、5……
products.product_id  ：1、2、3、4、5……
```

两个字段可以由各自独立的序列生成。即使值域、唯一率和重叠指标相同，也不能证明它们指向同一种业务实体。扩大采样甚至全量比对，都不一定能解决这种歧义。

**建议禁止仅凭数据重叠自动接受推断关系，保留样例数据作为已有业务关联依据的验证手段。**

不建议直接禁止整数类型关联，也不建议删除所有数据验证。大量真实外键本来就是整数，问题在于接受关系的证据不足。

## 2. 当前代码的保护边界

### 2.1 标准 rel 路径已有名称门槛

[candidate_generator.py](../../metaweave/core/relationships/candidate_generator.py) 在单列候选进入评分前检查类型兼容度和名称相似度。当前 [metadata_config.yaml](../../configs/metadata_config.yaml) 配置如下：

| 配置 | 当前值 | 含义 |
|---|---|---|
| `single_column.min_type_compatibility` | 0.8 | 最低类型兼容度 |
| `single_column.name_similarity_important_target` | 0.6 | 关键目标字段的名称相似度门槛 |
| `single_column.name_similarity_normal_target` | 0.9 | 普通目标字段的名称相似度门槛 |
| `composite.name_similarity_important_target` | 0.6 | 复合键特权匹配中对应字段的名称门槛 |

复合键匹配也存在名称约束，包括逐字段阈值检查及同名匹配路径。

因此，若代码实际计算的名称分数低于配置门槛，当前标准单列路径应提前拒绝该候选。不能仅凭误判现象就认定当前存在一个可以独立删除的“忽略名称、纯数据兜底”分支。

需要进一步通过真实误判产物和日志区分：

- 人认为含义无关，但字段名 Embedding 分数超过门槛。
- 两个字段都叫 `id`，名称相似度直接达到 1。
- 候选来自 `rel_llm`，随后被综合评分接受。
- 实际运行版本或配置与当前仓库不同。

### 2.2 名称分数不是中文业务含义验证

[name_similarity.py](../../metaweave/core/relationships/name_similarity.py) 比较字段名字符串或字段名 Embedding。同名字段会直接返回 1。

该分数没有同时引入表名、中文注释和业务实体上下文，因此不能等同于“两个字段的中文含义相同”。字段名不同也不保证 Embedding 分数低于门槛。

### 2.3 综合评分允许数据指标补偿名称不足

当前权重为：

```text
总分 = 0.55 × 包含率
     + 0.20 × 名称相似度
     + 0.15 × 类型兼容度
     + 0.10 × Jaccard
```

当前配置的接受阈值为 `decision.accept_threshold: 0.65`。

如果名称相似度为 0，其他三项均为 1：

```text
总分 = 0.55 + 0 + 0.15 + 0.10 = 0.80
```

这说明评分公式自身不要求名称或业务语义支持。该算例以候选已经进入评分阶段为前提，并不意味着标准候选生成会放行名称分数为 0 的字段对。

标准路径的最终接受逻辑主要按综合分数过滤，再执行复合关系对单列关系的抑制；`rel_llm` 的最终阈值过滤也主要检查综合分数。

代码依据：

- [scorer.py](../../metaweave/core/relationships/scorer.py)
- [decision_engine.py](../../metaweave/core/relationships/decision_engine.py)
- [llm_relationship_discovery.py](../../metaweave/core/relationships/llm_relationship_discovery.py)

本次未连接数据库复现用户的具体误判，因此以上确认的是机制风险，尚未定位某条实际误判的完整来源。

## 3. 推荐的决策机制

### 3.1 先检查关联依据，再进行数据验证

建议把业务依据作为独立准入条件，避免仅作为可被其他分数补偿的加权项：

```text
明确物理外键
    → 保留为显式关系并记录来源

人工确认的字段映射
    → 检查结构有效性并保留来源

其他推断候选
    → 检查实体与字段角色是否匹配
    → 检查类型并进行数据验证
    → 接受、拒绝或保留为待确认候选
```

物理主键、唯一约束或索引只说明字段自身结构，不能单独证明两张表之间存在关联。应区分物理外键与这些单表约束。

### 3.2 业务依据应包含上下文

判断时可使用：

- 表名、表注释及所属业务实体。
- 字段名、中文注释及标识对象。
- 经确认的字段映射、别名规则或业务规则。
- 必要时使用带上下文的语义判断。

| 字段对 | 推荐行为 |
|---|---|
| `orders.customer_id` → `customers.id` | 有实体指向依据，可进入数据验证 |
| `customers.id` → `products.id` | 不能因同名和数值重叠就接受 |
| `customer_no` → `khbh`，且确认属于同一客户标识体系 | 支持异名关联并进行数据验证 |
| 无注释、无上下文的两个独立整数编号 | 证据不足，不自动建立关系 |

名称不同不等于业务不相关，名称相同也不等于业务相关。避免把提高名称门槛作为唯一解决方案。

LLM 可辅助判断实体和角色，但其结论不能自动视为可靠证明；明确的语义冲突应拒绝，依据缺失或不确定时应保留为待确认候选。

### 3.3 保留数据验证

包含率等指标仍可用于检验候选是否得到数据支持、发现明显不匹配，并辅助估计基数。

其定位应是验证关联假设，而不是从整数值重叠独立推导业务关系。多个重叠指标也不一定是独立证据，不能仅因它们同时较高就认为业务关联已被确认。

## 4. 开关与删除策略

当前检查未发现专门表达“是否允许纯数据自动接受”的独立开关。可新增如下配置：

```yaml
relationships:
  inference:
    allow_data_only: false
```

**以上为拟议配置，当前代码尚未支持，名称和具体结构可在设计时调整。**

关闭时的语义应为：缺少业务关联依据的推断候选，无论数据重叠分数多高，都不能自动接受。

实施要求：

- 同时约束 `rel` 和 `rel_llm`，不能只修改标准路径的决策引擎。
- 对纯数据候选记录拒绝或待确认原因，避免无法追溯。
- 不改变显式物理外键的来源分类。
- 如果候选阶段可以确定证据不足，提前排除以减少无效采样；最终接受阶段仍保留统一检查。
- 在实现开关前定义“业务依据存在”的具体规则，否则开关本身无法解决误判。

推荐默认禁止纯数据推断的自动接受。如果保留探索能力，此类结果仅进入待确认产物，不写入正式关系图。若无探索需求，可以直接删除这种自动接受行为，不必维护可重新放开的高误判策略。

## 5. 不建议单独采用的措施

| 措施 | 不足 |
|---|---|
| 全面禁止整数关联 | 会丢失大量真实整数外键 |
| 只提高综合分数阈值 | 同名独立 ID 仍可能取得很高分数 |
| 只提高名称相似度门槛 | 无法解决 `id` 同名异义，也会漏掉异名真实关系 |
| 只增加采样量 | 独立编号体系仍可能具有高度重叠值域 |
| 只增加唯一率要求 | 两套独立主键都可能完全唯一 |
| 单纯更换 Agent 或模型框架 | 不会自动修复证据准入与评分补偿问题 |

## 6. 验证与回归建议

首先收集实际误判的输入画像、关系产物和运行日志，确认发现路径、候选类型、名称分数、数据分数及使用配置。

随后至少覆盖以下用例：

| 用例 | 预期 |
|---|---|
| 两个异名、异义的独立自增 ID，样例重叠高 | 不自动接受 |
| 两个都叫 `id`、但实体不同的字段 | 不因同名放行 |
| 名称不同但经确认指向同一实体标识的真实关系 | 保留发现能力 |
| 明确物理外键 | 保留显式关系 |
| 语义支持但数据明显冲突的推断候选 | 不因语义支持直接接受 |
| 缺少注释与上下文的高重叠整数候选 | 拒绝自动接受或输出待确认 |
| `rel_llm` 提出错误候选且数据分数很高 | 最终准入规则能够拦截 |
| 复合键中包含通用整数分量 | 按完整键映射及实体语义判断，不能仅看单个分量重叠 |

比较时分别统计误报、漏报、待确认数量及采样开销，避免只看接受关系总数。关闭后的回归测试还应验证相关配置确实在两条发现路径生效。

## 7. 取舍与后续步骤

该策略可能降低召回率：没有可用命名、注释、约束或人工映射的真实隐式关系，可能不再被自动发现。

对于会影响下游 JOIN 和 SQL 正确性的正式关系图，建议优先减少错误关联，允许对证据不足的候选暂不下结论。

下一步应先定位真实误判样例，再明确实体与字段角色准入规则，以及是否需要待确认探索模式。当前不建议在未定位具体路径前直接删除整个候选生成或数据评分模块。
