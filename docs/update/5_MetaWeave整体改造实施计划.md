# MetaWeave 整体改造实施计划

日期：2026-09-10  
状态：已确认实施顺序；具体接口和技术细节按阶段设计，尚未实施代码改造。

## 1. 目标与已确认决策

本轮改造面向关系发现质量、作业服务化、模型调用层升级及容器化交付，保留现有 CLI 和核心业务能力。

已确认的方向：

- 优先解决整数编号值域重叠造成的错误关联，禁止缺少业务依据的纯数据候选自动进入正式关系结果。
- 提供 REST API，通过接口提交后台作业、查询状态并获取结果。
- REST API 与 CLI 共用业务服务，保留容器内手工执行命令的能力。
- 保留 Milvus + PostgreSQL + Neo4j，暂不启用 pgvector，也不实施向量库迁移或双写。
- 升级现有 LangChain 相关依赖和统一模型调用层；LangGraph 按恢复需求评估，暂不将 Deep Agents 引入主流程。
- 使用 Docker Compose 统一启动最终部署所需服务。

当前仓库尚未使用 LangGraph，也未发现自定义 ReAct Agent。对话历史属于可能的下游职责，不作为当前 MetaWeave 已有功能或本轮默认新增范围。

## 2. 已确认的实施顺序

用户选择原建议的 **3 → 4 → 1 → 2 → 5 → 6** 顺序，并同意将 API 开发必需的最低限度作业规范前置到 API 阶段开始时确定。

| 新阶段 | 工作 | 对应原顺序 |
|---|---|---|
| 1 | 优化关系发现策略 | 原 3 |
| 2 | 确定最低作业规范，实现统一作业服务与 REST API | 原 4，并包含原 1 的必要前置部分 |
| 3 | 根据实际实现收敛整体架构与部署边界 | 原 1 的其余部分 |
| 4 | 升级 LangChain 与模型调用层 | 原 2 |
| 5 | 完成 Dockerfile 与 Docker Compose 部署 | 原 5 |
| 6 | 端到端验收与发布 | 原 6 |

该顺序优先改善业务正确性，再建立服务接口，随后升级底层依赖并完成部署。每个阶段都执行相应验证，第 6 阶段不是首次测试，而是最终集成验收。

## 3. 阶段 1：优化关系发现策略

### 目标

减少独立整数编号、同名异义字段等高重叠数据造成的误关联，保留有业务依据的真实关系发现能力。

### 工作范围

1. 收集真实误判样例，核对运行版本、配置、候选来源及评分明细。
2. 明确业务关联依据的准入规则，区分显式物理外键、人工映射和推断候选。
3. 禁止缺少业务依据时通过数据分数补偿并自动接受关系，同时约束 `rel` 与 `rel_llm`。
4. 保留类型检查和样例数据验证，不全面禁用整数关联，不删除整个评分模块。
5. 明确证据不足候选的处理方式：拒绝，或单独输出为待确认结果。
6. 如保留探索模式，设计默认禁止纯数据自动接受的配置，并记录拒绝或待确认原因。

### 验收条件

- 独立自增 ID、同名异义字段不会仅因高重叠而自动接受。
- 有明确依据的异名真实关系仍可进入数据验证。
- 显式外键的来源分类和输出得到保留。
- 两条发现路径均经过回归验证。
- 记录误报、漏报及待确认结果的变化，不仅比较关系总数。

详见 [4_关系发现纯数据误判分析与改造建议.md](4_关系发现纯数据误判分析与改造建议.md)。

## 4. 阶段 2：统一作业服务与 REST API

### 4.1 先确定最低限度的作业规范

以下事项是实现 API 的前提，不能全部延后到阶段 3：

- 首期开放的生成、关系发现及加载作业范围。
- 作业 ID、参数、状态转换、进度、错误和结果引用。
- 后台作业由谁执行、如何领取及更新状态。
- 并发限制、输出目录隔离、目标数据集更新和清理范围。
- CLI 作业是否统一登记并可由 API 查询。
- 进程重启后如何处理未完成作业。

无需此时确定所有远期扩展能力，但必须形成可执行的一致约定。取消、失败重跑和断点恢复是不同功能，应分别确定首期范围；不能将状态持久化视为已经实现断点恢复。

### 4.2 实现业务服务与 API 闭环

从 CLI 编排中提取可直接调用的业务服务，让参数解析与实际处理分离：

```text
CLI / REST API
      ↓
统一业务与作业服务
      ↓
元数据生成 / 关系发现 / 数据加载
```

API 不通过拼接 shell 命令调用 CLI 来复用业务功能，也不直接绑定 LangChain 的具体类型和调用细节。

首期完成：

```text
提交作业 → 返回作业 ID → 后台执行 → 查询状态 → 获取结果
```

使用 PostgreSQL 保存作业状态等控制数据。API 框架、队列与 worker 的具体实现需在本阶段设计时确定，当前不预先指定新增组件。

### 验收条件

- 长作业在后台执行，提交接口返回作业 ID。
- 状态、错误和结果位置可查询并持久化。
- 并发作业不会互相覆盖产物或不受控地清理同一数据集。
- CLI 原有核心能力可继续使用，其作业登记行为符合已定规范。
- 进程中断后的作业状态与处理策略得到验证。

## 5. 阶段 3：整体架构收敛

### 目标

根据阶段 2 的实现确定完整运行边界，为框架升级和最终部署提供稳定结构。本阶段不从头重做作业模型，也不将运行必需的设计拖到此时才处理。

### 工作范围

- 确认 API、worker 和 CLI 的进程职责，以及最终是否拆分容器。
- 确认业务服务与模型调用层的接口边界。
- 明确 PostgreSQL、Milvus、Neo4j 的数据归属和生命周期。
- 确认产物版本、存储位置、更新范围及可重建方式。
- 明确数据源配置、环境变量、初始化与运行权限需求。
- 对向量存储做必要接口隔离，暂时只维护 Milvus 后端。

### 推荐数据职责

| 组件 | 职责 |
|---|---|
| PostgreSQL | 作业、配置、执行状态、错误、产物引用等控制数据 |
| Milvus | 表结构、维度值及 SQL 样例向量 |
| Neo4j | 表、字段和关联关系 |
| 持久化文件存储 | DDL、JSON、Markdown、Cypher、日志等产物 |

### 验收条件

- 形成与实际代码一致的模块及部署边界说明。
- 确认部署服务清单、启动方式、连接关系和持久化要求。
- 不重复维护两套业务编排或两个向量后端。

详见 [2_Milvus与pgvector评估及存储选型建议.md](2_Milvus与pgvector评估及存储选型建议.md)。

## 6. 阶段 4：LangChain 与模型调用层升级

### 工作范围

1. 重新核对实施时最新非预发布版本，解析并锁定兼容依赖组合。
2. 保留统一 `LLMService` 入口，验证千问和 DeepSeek 接入、参数透传及模块配置覆盖。
3. 整理响应类型、错误分类、SDK 与应用层重试职责和调用指标。
4. 逐步为 JSON 类任务引入结构化输出，保留业务校验及必要回退。
5. 仅在已确认需要持久化工作流恢复时评估 LangGraph。

当前不计划整体 Agent 化。Middleware 用于确实采用 Agent 的执行循环，不为替换普通调用中的重试、日志而强行引入 Agent。

### 验收条件

- 同步、异步、超时、失败和重试行为符合约定。
- 模块级模型覆盖保持有效。
- 阶段 1 的关系发现回归和阶段 2 的 API 作业流程通过验证。
- 产物结构兼容，固定样例与小规模真实调用未出现不可接受的质量退化。
- 升级后的依赖组合写入锁文件。

详见 [1_LangChain升级与Agent机制改造建议.md](1_LangChain升级与Agent机制改造建议.md)。文档中的版本仅为讨论时快照，实施时重新核对。

## 7. 阶段 5：Dockerfile 与 Docker Compose

### 工作范围

- 构建独立 Linux Python 镜像，使用锁定依赖，配置 CLI、工作目录与启动命令。
- 根据阶段 3 确定的结构配置 API、worker；需要拆分时可复用同一镜像。
- 编排 PostgreSQL、Milvus、Neo4j 及所选部署必需的组件。
- 配置持久卷、产物和日志挂载、环境变量及容器网络。
- 实现健康检查和必要初始化，区分进程启动与服务可用。
- 保留连接 Docker 外部源数据库的能力。
- 提供容器内 CLI 和临时任务容器的运行说明。

### 验收条件

- 可通过 Compose 按说明统一启动服务。
- 可提交 API 作业，也可通过容器手工执行 CLI。
- 容器重建后，数据库和持久化产物仍保留。
- 初始化可重复执行且不会意外覆盖既有业务数据。
- CLI 与 API 的共享资源符合并发和隔离规则。

开发阶段可提前使用 Compose 启动数据库或验证镜像，阶段 5 负责最终编排与交付配置。详见 [3_REST_API与Docker_Compose改造顺序建议.md](3_REST_API与Docker_Compose改造顺序建议.md)。

## 8. 阶段 6：端到端验收与发布

### 验证范围

- 从源数据库提取到关系发现、产物生成及目标存储加载的完整流程。
- 标准路径与 LLM 路径的关键回归场景。
- API 提交、执行、状态查询、结果获取和错误报告。
- CLI 与 API 共存及并发隔离。
- 数据库不可用、模型调用失败、进程中断和容器重启后的既定处理行为。
- 数据持久化、全量刷新和增量更新的范围。

### 交付内容

- 可复现的依赖锁文件与镜像构建配置。
- Compose 配置及不含真实凭据的环境变量示例。
- CLI、API、部署、初始化与升级运行说明。
- 测试结果、已知限制，以及尚未实现的可选能力清单。

具体发布目标和镜像仓库尚未确定，准备交付物与向外部仓库推送镜像应区分处理。

## 9. 执行原则与范围控制

- 每个阶段完成后进行相应验证，再推进依赖该结果的下一阶段。
- 优先复用现有可运行逻辑，不把服务化扩大为算法重写。
- 不实施 pgvector 替换或 Milvus/pgvector 双写。
- 不因版本升级默认引入 Deep Agents、LangGraph 或额外队列。
- 不在本计划中承诺尚未设计的断点恢复、取消或分布式扩容能力。
- 在 WSL/Linux 中使用项目规定的 `.venv-wsl` 验证代码；容器内独立构建环境。
- 用户后续确认的需求变化应更新本计划及对应专题文档，保持决策和实现一致。
